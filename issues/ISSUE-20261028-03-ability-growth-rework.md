## 现状

### 玩家侧

| 项 | 现状 |
|---|---|
| 属性点发放 | `finishLevel()` 里**每通关 1 关**就 `playerStats.abilityPoints += ABILITY_POINTS_PER_LEVEL`（常量 = 1） |
| 加点上限 | `ABILITY_CAP = 20`，`drawRadar` 与加点点击都按这个校验 |
| 升级 | `openLevelUp()`：`heroLevel += 1`，`levelHpBonus += max(0, abilityMod(con))`，**回满血**，再从 8 个奖励里 3 选 1 |
| 升级频率 | `LEVELUP_EVERY_N_LEVELS = 3`（第 3/6/9… 关通关时） |
| HP 公式 | `maxHp = con + levelHpBonus + buffHpBonus()` |

**问题**：属性点和升级是两条**互不相关**的线——属性点每关都给，等级每 3 关才涨。

### 敌人侧

`ENEMY_STATS` 是**完全固定的常量面板**（代码注释原文：「敌人固定面板（无成长）」）：

| 敌人 | 六维 | HP | AC | 移动 | 熟练 | 伤害 |
|---|---|---|---|---|---|---|
| 骷髅 | 力10 智6 敏6 感6 魅3 体10 | 10 | 9 | 3 | +1 | 1 |
| 幽灵 | 力8 智8 敏10 感8 魅6 体6 | **2（`hpFixed` 写死）** | 9 | 5 | +2 | 1 |
| 外星人 | 力0 智10 敏8 感8 魅6 体8 | 8 | 9 | 4 | +2 | 1 |

`computeEnemyHp(type)` 只返回 `hpFixed ?? con`，没有任何成长项。三种敌人的 AC 恒为 9（「敏+体」都等于 16 的公式巧合）、伤害恒为 1（`max(1, 1+力调)` 把 0/−1/−5 全截平）。

## 期望

### 1. 玩家：属性点绑定升级，每次升级给 2 点

- **取消**「每通关 1 关给 1 点」。
- **改为**「每次升级（第 3/6/9… 关通关）给 2 点」。
- 2 点**自由分配**，允许都加同一项（受 `ABILITY_CAP = 20` 约束）。
- 常量改名以免误导：`ABILITY_POINTS_PER_LEVEL = 1` → `ABILITY_POINTS_PER_LEVELUP = 2`。
- `enterAllocGate()` 的闸门逻辑天然兼容：非升级关 `abilityPoints` 恒为 0，会直接进下一关；升级关为 2，会强制加完才放行。

**发放时序**：`finishLevel()` 里现有 `abilityPoints += …` 挪到 `openLevelUp()`（即叠加到 `heroLevel += 1` 那次），保证「点数和等级同时到账」。

### 2. 敌人：每关随机提升 1 项属性，只从当前最高的 4 项里选，相邻两次不重复

- **每个敌人个体**在每一关都经历 1 次属性提升 → **第 L 关的敌人已经历 L 次提升**（第 6 关的敌人提了 6 次）。
- 每次提升时，**按当时**的属性值取**最高的 4 项**作为候选池（提升后排序会变，下一次要重新算）。
- 排除**上一次**被提升的那一项（相邻两次不重复；隔一次可以再提同一项）。
- 每次选中项 `+1`，上限 `ABILITY_CAP = 20`；达到上限的属性从候选池剔除。
- 并列时的取序：按 `ABILITY_ORDER = ['str','dex','con','int','wis','cha']` 稳定排序，保证可复现。

### 3. 敌人：每 3 关升级一次，HP 上限算法与角色一致

- 敌人等级 = `⌊关卡 / 3⌋`（第 3/6/9… 关各升 1 级）。
- 每次升级：`enemyLevelHpBonus += max(0, abilityMod(con当前值))`。
- **HP 上限 = con + enemyLevelHpBonus**，与角色 `maxHp = con + levelHpBonus` 完全同构。
- **幽灵取消 `hpFixed`**，统一走体质（HP 从 2 → 6 起步），保持「和角色一样」。
- 同一关内生成的敌人，HP 直接取算好的上限（每关都是新生成的满血单位）。

**每关的结算顺序**：先做本关的属性提升 → 再判断是否升级 → 再生成单位。即第 3 关的敌人是「提了 3 次属性、升了 1 级」之后的面板。

### 4. 派生值自动跟随（无需额外写代码）

属性涨了，下面这些都通过现有函数自动变化，**属于预期行为**：

| 派生值 | 公式 | 影响 |
|---|---|---|
| `ac` | `5 + ⌊(敏+体)/4⌋` | 敌人变难命中 |
| `move` | `⌊敏/2⌋` | 敌人跑得更快 |
| `meleeDmg` | `max(1, 1+力调)` | 力量涨 → 近战伤害涨 |
| `rangedDmg` | `max(1, 1+智调)` | 智力涨 → 外星人射击伤害涨 |

⚠️ 这意味着敌人强度是**四维同时提升**，比单纯加 HP 猛烈得多，平衡段落已列风险与收敛选项。

### 5. 可复现性（实现关键）

敌人每关重新生成（`initLevel()` 里 `enemies = []`），**没有跨关的个体身份**。因此不能"记住某个敌人"，而要在生成时**推演**：

现有可用 API（**已核对，不要臆造 `mulberry32` / `hashStr`**）：
`seedRng(s)` 设置全局滚动状态 `RNG_SEED`、`rng()` 取随机、`randInt(n)`、`pvpRng(seed)` 是独立工厂。
全局 `rng()` **有滚动状态**，用它算成长会导致「每次重绘敌人面板都换一批属性」，绝对不能用。

需要新增两样东西：

```js
/* 1) 记录本局初始种子。RNG_SEED 会滚动，不能当种子用。
 *    在 seedRng() 里同步记录；选角开局时锁定，关卡内不得重掷。 */
let RUN_SEED = 1;
function seedRng(s) {
  RNG_SEED = (s >>> 0) || 0x9E3779B9;
  if (RNG_SEED === 0) RNG_SEED = 0x9E3779B9;
  RUN_SEED = RNG_SEED;                     // ← 新增这一行
}

/* 2) 敌人成长专用随机：与全局 rng() 完全隔离（同 pvpRng 的实现，但不落在 PVP-CORE 区间内，
 *    避免影响「单测按 PVP_CORE 标记切片」的约定）。 */
function enemyGrowthRng(seed) {
  let a = (seed >>> 0) || 0x9E3779B9;
  return function () {
    a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

/* 生成第 level 关的第 idx 个敌人时，从 L1 推演到 Llevel。
 * 种子由「本局种子 + 关卡序号 + 实例下标 + 类型序号」混合 → 同一局同一关结果稳定，
 * 重绘/刷新不会抖动（本项目「意图可预判」的硬要求，参见 enemyAggression 的注释）。 */
function computeEnemyGrowth(type, level, idx, runSeed) {
  const a = { ...ENEMY_STATS[type].abilities };
  const typeIdx = ENEMY_TYPES.indexOf(type);          // 0/1/2
  const rnd = enemyGrowthRng((runSeed + level * 131 + idx * 977 + typeIdx * 7919) >>> 0);
  let hpBonus = 0, lastKey = null;

  for (let lv = 1; lv <= level; lv++) {
    /* 1) 属性提升：当前最高的 4 项，排除上一次的选择 */
    const top4 = ABILITY_ORDER
      .filter(k => a[k] < ABILITY_CAP)
      .sort((x, y) => (a[y] - a[x]) || (ABILITY_ORDER.indexOf(x) - ABILITY_ORDER.indexOf(y)))
      .slice(0, 4)
      .filter(k => k !== lastKey);
    if (top4.length) {
      const pick = top4[Math.floor(rnd() * top4.length)];
      a[pick] += 1;
      lastKey = pick;
    }
    /* 2) 每 3 关升级：HP 加成本与角色同构 */
    if (lv % 3 === 0) hpBonus += Math.max(0, abilityMod(a.con));
  }
  return { abilities: a, maxHp: a.con + hpBonus, level: Math.floor(level / 3) };
}
```

> **`top4` 与 `lastKey` 的边界**：若上一次选的属性恰好掉出最高 4 项，`filter(k => k !== lastKey)` 无副作用；
> 若所有可提升属性都已到 `ABILITY_CAP`，`top4` 为空数组，本次跳过（不死循环）。

调用处替换 `getEnemyAbilities(type)` / `getEnemyProf(type)` / `computeEnemyHp(type)`（`initLevel` 第 2546~2550 行）：
成长的属性值与 HP 用 `computeEnemyGrowth()` 的结果；`prof` 本次**不变**（见备注）。
`ENEMY_STATS` 保留为基础面板（初始值），不再直接作为运行时数值。

## 数值推演示例（一个固定种子下的序列，供实施后对照）

以骷髅为例，初始 `力10 敏6 体10 智6 感6 魅3`，最高 4 项 = 力/体/敏/智（魅 3 排除）：

| 关卡 | 提升次数 | 六维（力/敏/体/智/感/魅） | 升级次数 | HP 加成 | HP | AC |
|---|---|---|---|---|---|---|
| 1 | 1 | 11/6/10/6/6/3 | 0 | 0 | 10 | 9 |
| 3 | 3 | 11/7/11/6/6/3 | 1 | 0（体11 → 调整值 0） | 11 | 9 |
| 6 | 6 | 12/7/12/7/6/3 | 2 | +1 | 13 | 9 |
| 10 | 10 | 13/8/13/8/6/3 | 3 | +2 | 15 | 10 |
| 20 | 20 | 约 15/11/15/11/6/3 | 6 | 约 +12 | 约 27 | 11 |

**注意两个现象**：

1. **前期 HP 几乎不涨**——体质 11 的调整值是 0，第 3 关升级不给血。这是「算法和角色一样」的直接后果（角色同样如此）。
2. **第 20 关敌人 HP 约 27，而玩家单回合伤害上限 6** → 单个骷髅要打 4~5 回合，6 个敌人约 27 回合清场。这是**显著加难**，见下方风险。

## 平衡影响与风险

| 变化 | 玩家 | 敌人 |
|---|---|---|
| 属性成长 | 每关 1 点 → **每 3 关 2 点**（20 关累计 20 → **12 点**，−40%） | 0 → **每关 +1**（20 关累计 +20 点，分散在最高 4 项） |
| HP | 不变（每 3 关升级 +体质调整） | 固定 → **每 3 关升级 +体质调整** |
| 命中/伤害/移动 | 随属性点上涨 | **随属性自动上涨（本次新增）** |

净效果：**双向拉近**，且敌人侧涨幅快于玩家（每关 vs 每 3 关），中后期会明显变难。

⚠️ **这是本次规格的必然结果，不建议在实现时自行打折**。但若实测过难，以下收敛手段任选（需人类维护者拍板）：

1. 敌人属性提升**降频**为每 2 关 1 次（20 关 +10 点）；
2. 敌人属性提升**设总次数上限**（如最多 6 次，第 7 关后停止）；
3. 敌人 HP 加成改为**每 3 关固定 +1**，不用体质调整（避免体质滚雪球）；
4. 加大玩家属性点（每 3 关 3 点）。

**验收方式**：实现后必须用 `roguechess-autotest` 跑 ≥20 局，对比改动前后的「平均存活关卡 / 平均击杀」。若平均存活关卡下降超过 40%，视为需要回调。

## 验收标准

- [ ] 第 1、2 关通关后**不获得**属性点，第 3 关通关后获得 **2 点**，且此时角色等级同时 +1

## 备注

- **`prof`（熟练加值）本次不改**：人类维护者只提到属性和 HP。若后续需要敌人熟练随等级上涨（用于对抗玩家 `prof = 4 + ⌊(关-1)/5⌋` 的膨胀），另行提 issue。
  相关讨论见 `ISSUE-20261028-02-enemy-scaling.md` 的「待确认：玩家熟练曲线」。
- **玩家熟练曲线的隐患仍在**：即使敌人属性大涨，玩家第 20 关命中加值仍是 `+5(属性) + 7(熟练) = +12`，敌人 AC 约 11 → 命中率仍接近 95%。敌人的「变难」主要体现为**血更厚、伤害更高、跑得更快**，而不是「更难命中」。这一点需在实测时留意。
- **与 issue-01 的联动**：风笛冲锋改「剩余移动步数 = 攻击次数」后输出大幅提升；本次敌人成长会抬高敌人 HP，两者方向相反、可部分抵消，**必须一起跑平衡回归**，不要单独评估任一项。
- **实现顺序建议**：先做玩家侧（改动小、可独立验证），再做敌人侧（需要新增 `computeEnemyGrowth` 与日志适配），最后跑 autotest 统一回调数值。
