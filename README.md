>    `endHp` 在 `onLevelClear()` 里**华法琳吸完场上血迹之后**取（取早了等于每关白扣她一截血）。
>    关内吃 ❤️ / 🩸 的净回血会让差值为负，**必须夹 0**：不夹不只是「负经验」，`eff = ref − hpLoss` 会超过 `ref`，
>    经验突破 24 上限，保底/上限两条算术保证同时失效。
> 3. **每关经验**：`ref = clamp(round(levelStartHp × 0.4), 2, 8)`，`eff = clamp(ref − hpLoss, 0, 6)`，
>    `xpGain = 12 + 2 × eff`，恒在 **[12, 24]**。效率基准挂「本关开始血量」而不是 `maxHp`，
>    否则「带 1 HP 进关 → 物理上掉不了血 → 每关都算零失血 → 永久满效率」，反而残血最赚。
> 4. **关末不回血**（维护者明确要求）：不新增任何休整结算，血量原样带进下一关，与旧版一致。
>    升级仍回满血，但它是 `setTimeout(…, 600)` 在**两关之间**执行的，经验在 `onLevelClear()` 里就已冻结 ——
>    **禁止**为了「统一血量口径」把经验结算挪到升级之后，否则回满血会把 `endHp` 抬到上限、每关白送满效率。
> 5. **升级计数**：`levelUpPending`（布尔）→ `pendingLevelUps`（次数）。一次通关最多连升 3 级，每次各弹一张奖励；
>    选完若还有待升级就接着弹，全部选完才进加点闸门（布尔装不下「一次升 2 级」，`if (0)` / `if (2)` 都是坑）。
> 6. **UI**：结算日志改成「行动 N 次 · 本关失血 X（开局 A → 结束 B，失血基准 R）→ 经验 +G（xp/阈值）」；
>    角色卡 `Lv.N` 下加一条 4px 方形经验条（沿用「方形=信息」）；开局规则说明同步改写，敌人成长说明保持原样。
>
> ### 数值自洽性（可验算）

> - 保底 `12 × 3 = 36 = XP_TABLE[1]` → **第 3 关必升，与水平无关**；单关上限 `24 < 36` → 第 1 关永远升不了；

## 0. 协作核心（必读）

### 0.0 铁律：不直接改游戏，先写 issue 文件

> **人类维护者 2026-10-28 定。本条效力高于 §0 其余条款和 §5 任务表。**
>
> **想改游戏 —— 新功能、UI 调整、数值平衡、bug 修复，一律先写一份 issue 文件放进 `issues/`，不要动 `game.html`。**
> **只有人类维护者明确说「版本更新 / 发版 / 开始更新」时，才一次性按 `issues/` 里的全部 issue 动手改游戏，改完删掉 issue 文件。**

看到 `issues/` 里有文件却在直接改 `game.html`，就是违规。审查代码时按这条查。

#### 为什么定这条（三个理由都有真实事故支撑）

| 理由 | 事实依据 |
|---|---|
| **并发覆盖会静默丢改动** | `game.html` 是单文件产物，推送是整文件覆盖语义。2026-10-27 一次险些覆盖他人 +53/−32 的 UI 改动；2026-10-28 又两次发现远程已被别人推进（`game.html` +722 B、`README.md` +3,859 B） |
| **碎片化改动把 CDN 缓存反复打穿** | Pages 走 Fastly，`Cache-Control: max-age=600`（见 §0.9）。每改一次都要等 10 分钟才能确认生效；攒成一批只付一次等待成本 |
| **需求应当先审再写** | 先落 issue，人类维护者能在代码写出来之前就否掉不想要的东西，省掉整轮返工 |

#### issue 文件规范

**位置**：仓库根目录 `issues/`（该目录存**需求文档**，不是代码，不参与发布）

**命名**：
```
issues/ISSUE-<YYYYMMDD>-<两位序号>-<英文短标签>.md
例：issues/ISSUE-20261028-01-set-panel-version.md
```
同一天多份则序号递增；英文短标签用小写连字符，便于一眼看出主题。

仓库里已放好可复制的模板：**`issues/_template.md`**（复制 → 改名 → 填内容），目录说明见 `issues/README.md`。

**模板（复制即用）**：
```markdown
# <一句话标题>

- **提出人 / 时间**：<名字> / <YYYY-MM-DD HH:mm>
- **类型**：feature | ui | balance | bug | perf | docs
- **优先级**：P0 线上不可玩 | P1 明显影响体验 | P2 优化项
- **状态**：draft | ready | implementing | done

## 现状
现在是什么样。有截图 / 复现步骤就贴上来。

## 期望
改完之后应该是什么样。**用可验证的句子写**，不要写「优化一下手感」这类无法验收的话。

## 涉及区域
大概动哪里：设置面板 / 战斗结算 / 技能 XX / 联机轮询 …；不确定就写「待定位」。

## 验收标准
- [ ] 可验证的第 1 条
- [ ] 可验证的第 2 条

## 备注
（可选）参考作品、边界情况、已知约束。
```

**状态流转**：

| 状态 | 含义 | 谁推进 |
|---|---|---|
| `draft` | 想法还不完整 | 提出方 |
| `ready` | 信息够开工了（验收标准已写） | 提出方 → 人类维护者过目 |
| `implementing` | 正在这一轮版本更新里实施 | 实施方（边做边勾验收项） |
| `done` | 已上线 | 实施方，**随即删除该 issue 文件** |

`done` 只是过渡态，不要留在仓库里 —— 历史在 git 提交记录里，不该在 `issues/` 里越堆越多。

#### 一轮「版本更新」的标准动作

人类维护者说「版本更新 / 发版 / 开始更新」时，按顺序做完：

1. `ls issues/` 列出全部 issue，按 **P0 → P1 → P2** 排序，同优先级按提出时间先后。
2. 逐份读完，**先回一句「本轮做哪几份、不做哪几份、为什么」**；有歧义当场问，不要猜着实现。
3. 一次性改 `game.html`（尽量一次提交，避免多次触发 Pages 部署）。
4. 跑回归（§0.4 交付前 8 项检查），补齐测试证据。
5. 按 §0.9 双 BUILD 同步改版本号 → 发布 → 3 步自检。
6. 删除已完成的 issue 文件；**未完成或决定不做的保留**，并在文件末尾写一句「本轮未做，原因：…」。
7. 在 §10.3 变更记录里写一行：本轮做了哪几份 issue、上线版本号。

**线上完全不可玩**（白屏 / 无法选角 / 无法结算）时可以先修再补 issue，但必须在提交信息里写明

### 0.6 冲突、回滚与事故处理

- **同文件并行修改**：小步提交（单次 <= 300 行语义改动），提交前 rebase 到最新 `main`；冲突时保留语义正确的版本并**重跑回归**，不得靠"选一边"了事。
- **禁止**：`push --force`、删除他人分支、回滚他人工作。
- **发布前覆盖保护（强制）**：`game.html` 是单文件产物，API 推送是**整文件覆盖**语义——两人同改时，后推的一方会静默抹掉先推那方的改动，且因 fast-forward 成功而不报任何错（2026-10-27 `P0.1-1` 真实事故：一次险些覆盖他人 +53/-32 的 UI 改动）。`net/push_api.py` 已内置保护：推送前比对远端该文件的 blob sha 是否命中「我的基线」，不命中即以退出码 **3** 中止。

  | 场景 | 该怎么做 |
  |---|---|
  | 刚 fetch/rebase 完，声明"我已对齐远端" | `python net/push_api.py --sync-baseline` |
  | 明确知道改动基于哪个提交 | `python net/push_api.py --base <commit-sha>`（优先级最高） |
  | **被拦下（退出码 3）** | ❌ 不要 `--force`；① 取回远端最新版 → ② 在其上重新叠加改动（rebase，不是覆盖）→ ③ 重跑回归 → ④ `--sync-baseline` → ⑤ 再推 |
  | 确知后果、执意覆盖 | `--force`（**唯一例外**，须在提交信息里写明理由与已知会丢失什么） |

  基线来源优先级：`--base` > `net/.push_baseline.json`（上次推送/对齐时记录）> 本地 git `HEAD`/`origin/main`；三者都无法判定时按"有风险"中止。
  判据是"远端当前这一版，是我所知道的那一版吗"——**误报（保守中止）远好过漏报（静默丢改动）**；中止信息里会给出 rebase 指引。
  判据只针对**本次要推的文件**，因此 `leaderboard.json` 的高频成绩写入不会误伤其他文件的推送。
  回归测试：`python net/push_guard_test.py`（离线 10 项，覆盖放行/拦截/强制/无法判定四条路径）。
- **回滚顺序**：① 上一版构建产物重新发布 → ② 还原对应提交 → ③ 定位原因（优先比对快照）。
- **事故记录**：任何 P0 事故（数据丢失 / 榜单造假 / 线上不可用）必须当天在 §10.3 记一行，并补一条 R-xx 或 TD-xx。

### 0.9 发布与版本号维护（每次发版必读）

线上入口：<https://aopze.github.io/ark-rogue-chess/>（DLC 外壳）→ iframe 加载 `game.html`。

**★ 双 BUILD 必须同时改**，否则玩家会继续看到旧版：

| 位置 | 变量 | 作用 |
|---|---|---|
| `game.html` | `window.__ARK_VERSION__.build` | 玩家自查版本（设置面板标题栏「设置」右侧显示 `v<build>`） |
| `index.html` | `var BUILD = '...'` | iframe 用 `game.html?v=<BUILD>` 拉取，**改变 URL 才能穿透 CDN 缓存** |

两处值必须相同，格式 **`MMDDHHmm`**（月日时分，8 位；如 `10282137` = 10 月 28 日 21:37）。同一天发多版靠时分自然区分，不再用 `a`/`b`/`c` 后缀（2026-10-28 由 `YYYYMMDDx` 改为此格式）。

**为什么必须改**：GitHub Pages 走 Fastly CDN，响应头 `Cache-Control: max-age=600`。
浏览器与边缘节点最长缓存 10 分钟；`?v=` 变化是最省事的强制刷新手段。
**发布后 10 分钟内仍可能看到旧版属于正常现象**，不要误判为「没上线」。

**发布后自检（3 步）**：

1. `GET https://api.github.com/repos/aopze/ark-rogue-chess/contents/game.html`
   解码 base64 后与本地 `cmp` 比对 —— **这一步确认「服务器收到了」，与 CDN 无关**。
2. `GET .../pages/builds/latest` 确认 `status: built`、`error.message: null`。
   **若为 `errored` / `Page build failed.`，不要急着重传文件** —— 多发文件发布（`upload_multi.js` 是**一文件一提交**）
   会在几秒内触发十来个 Pages 构建，GitHub 侧会因排队冲突批量失败，而仓库内容其实是好的。
   处理：`POST /repos/aopze/ark-rogue-chess/pages/builds`（无 body）请求一次干净重建，约 50 秒后回到 `built`。
   实测 2026-10-28 04:38 一次 10 文件的发布：10 个构建全 `errored`，手动重建后一次成功，
   产物 281,705 B 与本地逐字节一致。**判据永远是「构建状态 built + 线上字节数对」，不是「构建没红过」。**
3. 浏览器访问 `game.html?v=<新build>`，展开设置面板看标题栏版本号是否为新值。
   若仍是旧值：等满 10 分钟，或用无痕窗口（避免本地磁盘缓存叠加）。

> 排查「新版本没上线」时按这个顺序看，别一上来就怀疑部署脚本：
> **① 服务器内容对不对 → ② Pages 构建成没成功 → ③ CDN / 浏览器缓存过期没有。**

## 4. 可复用原则与经验

以下原则从本仓库已踩过的坑里提炼，后续所有阶段都以此为准。

**原则 1 · 产物必须是单文件，源码必须多文件。**
现状的最大优势是"双击即玩、可任意静态托管、可在 Telegram iframe 里跑"。因此模块化的目标不是拆成 ESM 多文件上线，而是 `src/**` 拆分 + 构建内联回单个 `game.html`。构建脚本是唯一的产物出口（P0.1-3）。

**原则 2 · 规则纯函数化，UI 只消费结果。**
PvP 的 `pvpResolveTurn(state, plans, seed)` 已经是正确范式：给同样的输入必得同样的输出。单人应并入同一条路径，UI 变成 `render(state)` + 播放 `events[]`。判断标准：`grep -r "document\." src/rules` 必须为空。

**原则 3 · 一切都是种子函数。**
随机只允许从注入的种子派生，且派生必须分层：`runSeed → floorSeed = hash(runSeed, level) → turnSeed = hash(floorSeed, turn)`。这样"整局可复现"和"单回合可复现"同时成立，也为服务端校验铺路。

**原则 4 · 先可回放，再可校验，最后才权威。**
不要一步跳到"服务端权威结算"。顺序是：回放文件（0.2）→ 计划合法性校验（0.4-a）→ 服务端重演校验（0.4-b）→ 服务端权威（0.4-c）。每一步都能独立交付并回滚。

**原则 5 · 一份规则代码，两端共用。**
服务端不要用 Python 重写规则。用 Node 加载同一份 `rules.bundle.js` 执行结算，HTTP 层语言无关。这样避免"两端规则漂移"这类最难查的问题。

**原则 6 · 发布边界写进流程，而不是记在脑子里。**
`index.html` 属 DLC、`net/` 属联机侧、`game.html` 属游戏产物。发布脚本只允许写 `game.html`；新文档/新代码走 PR，不混进发布脚本。历史上正是靠这条避免了覆盖用户 DLC。

**原则 7 · 每次改动都留快照。**
`demo_MMDDHHmm.html` + 双归档 = 免费的时间机器。任何"看起来是玄学"的问题，先二分快照。

**原则 8 · 移动端优先，但状态要从"窄"到"宽"验。**
先按 375–390 px 竖屏设计，再验横屏与桌面；每加一个悬浮 UI 都要问"它会不会挡住棋盘 / 挡住别的悬浮 UI"——空胶囊事件就是跨帧悬浮层的教训。

**原则 9 · 设置项一律持久化，且默认可回退。**
布局、比例、面板位置都进 `localStorage` 且带默认值；解析失败必须静默回退（现有代码的 `try/catch + null` 范式要保持）。

**原则 10 · 用可观测替代猜测。**
日志分类着色、版本号注入、`/api/health`、metrics，都属于"线上出问题能在 5 分钟内定位"的投资，优先级不低于新功能。

**原则 11 · `game.html`（及 `src/` 源码）必须为下游 Godot 正式版保留可对照结构。**
本仓库的游戏代码同时是另一份 Godot 工程（游戏正式版）的**玩法准绳**：对方逐模块复刻本仓库的规则与数值，并跑自有回归。因此本仓库的代码组织必须让"规则 / 数值"能被外部引擎低成本、无歧义地抄写——这是对所有 AI 协作方的硬约束，实施细则见 §10.4。

## 5. 分阶段计划

> 每个阶段都遵循同一结构：目标 → 任务 → 产出 → 验收 → 退出条件 → 风险。
> 阶段之间允许并行（例如 0.3 内容与 0.4 联机可由不同人推进），但**依赖关系不可跨**：0.2 的规则纯函数化是 0.4 权威化的前置。

### 5.1 阶段 0.1 · 原型整理（目标：能玩 → 可维护）

**目标**：在不改变任何玩法行为的前提下，把单文件原型变成"有构建、有版本、有回归"的工程基线。

**任务**

| 编号 | 任务 | 说明 |
|---|---|---|
| P0.1-1 | 冻结基线 | 打 tag `v0.1.0-prototype`；写 `CHANGELOG.md`；在产物注入 `window.__ARK_VERSION__ = {version, commit, builtAt}`，页内可查 |
| P0.1-2 | 建立目录 | 按 §6 落地 `src/ data/ build/ tests/ docs/`，先只搬运不重写 |
| P0.1-3 | 构建脚本 | `build/bundle.mjs`：按清单顺序内联 `src/**` 到 `templates/game.html` → 输出根目录 `game.html`；附"产物一致性校验"（对比旧版仅注释/空白差异）；**构建时自动注入 `__ARK_VERSION__.build` 并校验 `index.html` 的 BUILD（见 AC-23）** |
| P0.1-4 | 机械拆分 | 纯移动不改逻辑：常量与数据 → `src/data/`；掷骰与派生面板 → `src/rules/`；地图生成 → `src/rules/mapgen.js`；渲染 → `src/ui/`；联机 → `src/net/`；补丁与设置 → `src/ui/chrome.js` |
| P0.1-5 | 回归入库 | 现有 Playwright 脚本整理为 `tests/e2e/`（竖屏 / 横屏 / 选角 / 一关流程 / 设置面板 / 比例拖动 / 跨帧补丁），纳入 `npm test` |
| P0.1-6 | 调试口登记 | 列出 `__dbg` / `debugMode` / F12 钩子 / 临时日志，标注"保留 / 移除 / 移到 dev 构建" |
| P0.1-7 | 发布链路加固 | 发布脚本加"产物 sha 与版本号打印"；保留最近 10 版产物以便回滚 |

**产出**：可 `npm run build` 的仓库、首个 tag、首次入库的 e2e 测试、`docs/ARCHITECTURE.md` 骨架。

**验收标准**

- `AC-01`：`npm run build` 产出 `game.html`，与线上基线字节差 < 2%，且 e2e 全绿。
- `AC-02`：页面可读出 `window.__ARK_VERSION__`，与 tag 一致。
- `AC-03`：仓库根目录仍只含应有文件（`game.html`、`index.html`、`leaderboard.*`、`net/`、构建与测试配置），无临时脚本残留。
- `AC-04`：任意一次改动都能在 5 分钟内回滚到上一版（脚本一键）。
- `AC-23`：**双 BUILD 由机器把关**（§0.9），不再依赖"记得同时改两个地方"：
  - `game.html` 的 `window.__ARK_VERSION__.build` 由**构建脚本自动注入**（格式 `MMDDHHmm` 月日时分，如 `10282137`；同分钟连发自动顺延 1 分钟），人工不得手改；
  - 构建结束前自动比对 `index.html` 的 `var BUILD` 是否等于本次 build —— **不一致则构建失败并打印应改的值**。
    `index.html` 是只读资产（NB-01），脚本**只校验不改写**，改它仍需人类授权；
  - 本地试构建可用 `--no-build-check` 跳过该校验（仅本地，发布链路不得使用）；
  - 顺带消除 `P0.1-1` 的已知限制：`commit` 字段改为构建时注入真实 sha，不再是冻结的基线 sha。
  - 依据：2026-10-27/28 连续两次出现版本信息不同步（一次险些覆盖他人改动、一次排查"新版本没上线"实为 CDN 缓存），根因都是人工维护版本号。

**退出条件**：`v0.1.0-prototype` 打 tag，README 写明「改代码 → 构建 → 发布 → 回滚」四步。

**风险**：机械拆分引入的隐性顺序依赖（`let/const` 提升、初始化顺序）。缓解：拆分批次 ≤ 3 个模块/次，每批跑 e2e。

## 8. 禁止事项（红线）

| 编号 | 红线 | 原因 |
|---|---|---|
| NB-01 | 不得由发布脚本覆盖 `index.html` 或任何 DLC 文件 | 那是用户资产，历史上已明确边界 |

| NB-05 | 不得在未跑通回放金样的情况下合并规则改动 | 规则是最贵的回归面 |
| NB-06 | 不得用 `Math.random` 直接产生游戏随机 | 破坏可复现性 |
| NB-07 | 不得把 PvP 的 `gameover` 语义复用于联机结束 | 会向排行榜灌假成绩（已用 `pvp_over` 分离） |

| NB-09 | 不得在无人复核的情况下修改数值平衡表 | 平衡改动影响全部内容 |
| NB-10 | 不得跳过 e2e 直接发版（除紧急回滚） | 移动端布局回归成本远高于等待 5 分钟 |
| **NB-11** | **不得绕过 `issues/` 直接修改 `game.html`**（唯一例外见 §0.0） | 单文件产物 + 多 AI 并发 = 静默覆盖丢改动；碎片化改动还会把 CDN 缓存反复打穿 |

### 10.2 术语表

| 术语 | 含义 |
|---|---|
| run / 一局 | 从选角到死亡或通关的完整流程，由 `runSeed` 唯一确定 |
| 金样（golden） | 固定种子 + 固定计划 + 期望事件流哈希，用于回归比对 |
| 事件流 | 一次结算产生的有序事件数组（伤害、位移、技能、状态变化），可被播放也可被哈希 |
| 权威结算 | 由服务端计算并下发结果，客户端只负责播放 |
| 分层种子 | `runSeed → floorSeed → turnSeed` 的派生链，保证任意粒度可复现 |
| DLC 外壳 | 仓库 `index.html`，Telegram 容器与榜单生态，不属于游戏产物 |
| 单文件产物 | 构建后仍可直接双击运行、无外部请求的 `game.html` |

### 10.4 Godot 正式版复刻契约（下游兼容性）

> **地位**：本仓库的游戏代码（`src/` 源码 + 构建产物 `game.html`）是另一份 Godot 工程（游戏正式版）的**唯一玩法准绳**。Godot 端逐模块复刻本仓库的规则与数值，并跑自有回归（smoke / soak / layout / chars / tuner）。本契约保证"复刻"这一步低成本、无歧义。所有 AI 协作方在改动游戏代码时**必须**遵守以下 10 条。

**1. 源码多文件（沿用原则 1）**：所有逻辑在 `src/`，`game.html` 仅为构建产物；Godot 端复刻直接对照 `src/` 各模块，不读产物。

**2. 常量集中**：所有可调数值放在 `src/data/constants.js`（对应 Godot `Tuning.gd`），禁止在规则模块内散落魔法数字（如 `if (x > 3)` 应写成 `CONFIG.PLAYER_RANGE`）。

**3. 模块 / 符号命名对齐 Godot**：文件、函数、字段名尽量与 Godot 端 snake_case 一致（如 `char_id`、`player_effective_ac`、`skill_indices`、`planned_dodge_index`）；新增机制命名时先查 Godot 端是否已有对应符号，避免漂移。

**4. 数据表驱动**：角色 / 敌人 / buff 放在 `src/data/*.js`，字段名对齐 Godot `Characters.gd`（如 `char_id` / `abilities` / `prof`）。

**5. port-map 注释**：每个规则模块 / 关键函数上方写一行 `// @port <Godot文件>:<函数名>`，标注复刻目标。例：`// @port Battle.gd:attack_roll`。

**6. 规则层纯函数化（沿用原则 2）**：规则在 `src/rules/`，必须是**无 DOM 依赖的纯函数**；渲染 / DOM 只在 `src/ui/`。Godot 端复刻时只扫规则层。

**7. RNG 纪律（沿用 NB-06）**：随机一律走 `src/rules/rng.js` 的 `rng()`（mulberry32 单例 + `RUN_SEED` 分层派生），禁止 `Math.random()`。

**8. PVP 区段标注**：联机核心在 `src/net/pvp-core.js`，标 `// PVP (DEFERRED_IN_GODOT)`，Godot 端暂不复刻；**不得改动其接口语义**，以免 Godot 端后续对齐时错位。

**9. 变更摘要**：每次大改后，在 issue / commit 里附一段变更摘要——改了哪些 `constants.js` 键、新增 / 删除了哪些规则函数、数值增减。这是 Godot 端 `git pull` 后 re-audit 的输入。

**10. 对照映射表**（AI 改代码时对照此表，确保 Godot 端能找到对应实现）：

| 本仓库 `src/` 模块 / 符号 | Godot 端目标 |
|---|---|
| `src/data/constants.js` | `Tuning.gd`（全静态可调数值） |
| `src/data/characters.js` / `enemies.js` | `Characters.gd`（角色 / 敌人数据表） |
| `src/rules/rng.js`（`seedRng` / `rng` / `randInt` / `RUN_SEED`） | `Rng.gd`（mulberry32 单例） |
| `src/rules/dnd.js`（`abilityMod` / `computeAC` / `attackRoll` / `recomputePlayerDerivedStats`） | `Battle.gd`（DnD 派生与检定） |
| `src/rules/state.js` / `actions.js`（`playerChargeBudget` / 有效 AC / 动作预算） | `Battle.gd`（动作预算 / 闪避 / 技能节点） |
| `src/rules/buffs.js`（`damagePlayer` 统一受伤入口） | `Battle._damage_player`（统一伤害入口） |
| `src/rules/path.js`（路径判定 / 冲锋 / 步数统计） | `Battle.gd`（路径与技能节点） |
| `src/net/pvp-core.js` | Godot 端暂不复刻（DEFERRED_IN_GODOT） |
